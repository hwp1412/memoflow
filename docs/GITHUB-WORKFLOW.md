# 附录 B — MemoFlow GitHub 协作、验收与发布协议

> 文档 ID：MF-GITHUB-1  
> 适用范围：MemoFlow 0.1 → 1.0 的 AI Agent 参与开发  
> 关联：[AGENTS.md](../AGENTS.md) · [MF-US-1 算法规范](MF-US-1-SPEC.md)  
> 目标：**Agent 可开发、测试、推送功能分支并提交 PR；用户掌握最终验收、合并和正式发布权。**

## B1. 角色与权限

| 操作 | AI Agent | 项目所有者 |
|---|---|---|
| 阅读与分析仓库 | 负责 | 可查看 |
| 创建任务分支 | 经开发任务授权执行 | 可检查 |
| 修改代码、编写测试 | 经任务方案批准后执行 | 审核成果 |
| 将功能分支推送至 GitHub | 经仓库授权后执行 | 可审查 |
| 创建/更新 Pull Request | Agent 负责 | 可评论 |
| 自动化 CI 测试 | Agent 配置并检查（修改工作流需专项授权） | 查看结果 |
| 测试 Vault 的实际操作验收 | 提供步骤与证据 | **最终确认** |
| 合并到 `main` | **默认无权自行执行** | **最终决定并执行** |
| 创建稳定版 Git 标签/Release | **不得自行决定** | **明确授权** |
| 更新真实 Vault 或安装更新 | **默认禁止** | 用户主动操作/授权 |

Agent 可以使用**已授权且受信任**的本地 Git/GitHub 凭据进行推送，不得向对话索要账号密码、个人访问 Token 或将凭据写入仓库。若没有推送能力，交付本地 Commit、补丁或变更说明，让用户从自己的 Git 环境上传。

## B2. 分支策略

- `main`：稳定分支。只合并**已验收**的改动。
- `feat/<task>`：独立新功能，如 `feat/recursive-extract`。
- `fix/<task>`：独立缺陷修复。
- `refactor/<task>`：受控的非功能行为变更。
- `test/<task>`：测试设施改进。
- `release/<version>`：发布准备，只有经过批准才使用。

**每个任务一个分支，优先一个 PR。** 不能把多级摘录、调度、SR、PDF、发布流程混进同一个未经分别验收的大型 PR。

`main` 需要设置适当的 Branch Protection 或 Ruleset，建议开启 PR 合并要求、CI 必须通过、禁止 force push 和分支删除。是否能强制审批/限制管理员绕过，取决于当前仓库权限与 GitHub 配置。仅一个维护者时，不应设置无法满足的“必须另一人批准”规则。

## B3. 权限边界与停工条件

未经用户批准，Agent **不得**：

1. 直接向 `main` 推送代码。
2. 将尚未人工验收的 PR 合并。
3. 自动创建、移动或删除稳定版标签。
4. 发布 GitHub Release 或修改 Release 附件。
5. 绕过分支保护，或执行 force push。
6. 删除仓库历史、覆盖其他人的未提交更改。
7. 修改 GitHub Actions 的发布权限和自动发布触发条件。
8. 上传私人 Vault、测试私有内容、密钥或 Token。

出现合并冲突、权限错误、CI 失败、意外文件变更、真实 Vault 写入风险或不确定的远端状态时，应停止相关高风险操作，提供原因与解决方案，不得以覆盖性命令“先修好”。

## B4. 一次任务的固定协作流程

### 阶段 1 — 仅分析

用户示例：**“分析 M03，暂不修改。”**

Agent 必须给出：

- 现有行为与问题复现方法。
- 本次任务目标及非目标。
- 拟修改文件和可能影响的调用链。
- 旧版功能/旧数据保护点。
- 自动化测试计划、人工验收步骤。
- 回滚方案。
- 潜在阻塞项与需要单独授权的操作。

**未获批准不得开始高风险代码修改。**

### 阶段 2 — 批准实施

用户示例：**“批准 M03 方案，按约定范围开始开发。”**

Agent 在单独分支执行最小变更并自测；不得借机扩大任务范围。涉及 Frontmatter、调度字段、迁移、真实数据、GitHub 发布流程的新风险，应在继续前再次请求授权。

### 阶段 3 — 推送与创建 PR

仅在有 GitHub 权限、得到任务授权时：

1. 检查 `git status`、分支、Diff；确保无隐私文件和多余改动。
2. 提交带任务 ID 的 Commit。
3. 推送到对应**功能分支**。
4. 创建 PR，目标分支设为 `main`。
5. 记录 PR 地址、Commit SHA、测试结果和回滚说明。

Agent 可创建/更新 PR，但不能把“PR 已创建”写成“已验收、已发布”。

### 阶段 4 — Agent 自测报告

必须按本文件 **B5 模板** 提交待验收报告；已通过和未运行的测试严格区分。CI 失败或关键行为未验证时，状态为阻塞或待修复，而不是完成。

### 阶段 5 — 用户测试 Vault 验收

用户根据步骤实际测试：

- 新功能正确；
- 旧功能未回归；
- 真实用户数据未受开发过程影响；
- 必要的备份与恢复可用。

验收失败 → Agent 在**同一个任务分支与 PR** 中修复、补回归测试、重新提交报告。不能跳过失败项直接进入下一开发任务。

验收通过 → 用户明确回复“**M03 验收通过，允许合并**”；若没有授权，Agent 仍不得自主合并。

### 阶段 6 — 合并与记录

默认由**项目所有者亲自执行 Merge**。合并后 Agent 可在获准情况下核对合并 Commit、CI 和里程碑记录，但不能擅自创建正式 Release。

只有用户另外发出“**批准进入 M04**”才能进入下一项高风险任务。

- 分支：
- PR 地址：（无权限则说明原因）
- Commit SHA：
- 基线 Commit SHA：

（新增/修复的具体行为与未包含的范围）

## 2. 修改文件
（逐文件写理由；指出高风险文件）

## 3. 原有功能保护
（哪些旧操作必须不变；实际怎样验证）

## 4. 测试证据
- 实际执行的命令：
- 通过：
- 失败：
- 未执行及原因：
- CI 状态与链接：
（不能把“未运行”写成“通过”）

## 5. 用户手动验收步骤
1. 操作路径：
2. 预期结果：
3. 回归检查：
4. 异常/撤销操作：

## 6. 数据和兼容性影响
（旧 Frontmatter、调度、SR、data.json、迁移等）

## 7. 风险、限制与回滚
（代码回滚 Commit、数据备份/恢复方法）

## B6. 验收结果如何回复

项目所有者可以采用以下短句，确保授权边界清楚：

| 用户指令 | Agent 应做 |
|---|---|
| `分析 M03` | 只分析，不修改 |
| `批准 M03 方案` | 执行本任务开发、自测，按授权提交 PR |
| `提交 M03 验收报告` | 报告实际证据、待用户测试项 |
| `M03 验收失败：第 N 项不通过` | 只修复对应问题并重测 |
| `M03 验收通过，允许合并` | 记录通过；默认仍由用户点击 Merge |
| `M03 已合并，批准进入 M04` | 才能开始新任务 |
| `批准发布 v1.0.0` | 仅在全部发布质量门槛通过后，依单独发布计划执行 |

**“验收通过”不等于“批准发布”。“合并 PR”不等于“发布 Release”。**

## B7. GitHub CI 要求

PR 至少应触发正确的 MemoFlow 构建与测试，不得误构建上游原插件。

CI 应检查：

- 依赖安装与单元测试；
- MemoFlow 构建；
- `manifest.json` 的 `id` 确为 `memoflow`；
- 发布版本号的一致性；
- 对关键源码、算法和数据迁移的回归测试；
- 没有错误的 Release 附件路径。

若测试环境/配置尚未具备，先在 Phase 0 提交现状与补齐计划，不得把未配置的检查伪装成已执行。

## B8. 正式 GitHub Release 单独审批

发布与 PR 合并分开：

1. 提交候选版本、版本号、Release Notes、兼容性和升级影响。
2. 检查稳定分支中的 Commit、所有 CI、测试 Vault、迁移与回滚。
3. 明确构建输出使用 `dist/memoflow/` 的正确产物（以实际构建配置为准），不得误传根目录的上游文件。
4. 校验 `manifest.json`、Git Tag、Release 附件、插件 ID 和 SHA-256。
5. 经用户**单独明确批准**后创建正式标签/Release。
6. 发布后验证 Release 附件确实可下载安装；若失败按预定恢复方案处理。
7. 版本检测器默认使用正式 Release，而非 `main` 分支上的未发布代码。

**绝不自动覆盖 `data.json` 或修改真实 Vault。**

## B9. 推荐权限与最小风险实践

- Agent 只在可信的开发环境中使用已授权的 GitHub 权限。
- 优先让 Agent 推送**功能分支**，而不是拥有直接改写稳定分支的工作流。
- 不在聊天中传递密码、Token 或 SSH 私钥。
- 为 `main` 设置保护规则，关闭强推和删除。
- 若 GitHub 配置不支持预期强制规则，以人工审核和权限隔离补足；不能声称保护已配置。
- 每个 PR 保持范围小、测试可重复、回滚入口明确。
- 备份真实用户数据与 Git 提交历史是不同措施；代码恢复不代表数据自动恢复。

---

**协作总原则：Agent 负责开发、测试和提交 PR；用户负责实际验收、批准合并与授权发布。**
